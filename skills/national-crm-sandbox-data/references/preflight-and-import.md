# 対象環境の事前照合と投入

## 書込み前の停止条件

以下をローカル報告へ整理し、1件でも未解決なら全てのSalesforce書込みを止める。

- 認証先が未確定、Sandboxでない、組織IDが指定と異なる、作成者がシステム管理者でない。
- 実行モードで使用するオブジェクト・必要項目・必要RT・プロファイルがない、無効、利用不可。元と先で借入申込等の構造が異なる。
- 必須入力・選択肢・連動選択肢・制限・データ作成トリガーが不明。現行の自動処理が許可外データ・設定へ変更を及ぼす懸念がある。
- 支店コード・CIF・StaffID・窓口コードが0件または複数件。比較対象が同名でも別顧客の可能性がある。
- 外部IDのないレコードの重複識別が未確定、ユーザー作成モードでライセンス不足、親を再利用できない、保存結果が不確か。

業務データだけの投入では、未使用の70ユーザー用プロファイル・ライセンスの不足を停止理由にしない。担当者の有効性・区分・所属の照合は必要。

対象環境のDescribe、レイアウト、選択肢、既存レコード、必要時のフロー／Apex等の**読み取り**は許可される。設定変更は許可されない。過去のtest09の対応を根拠に、未実装項目を勝手に捨てたりRTをマスターへ置き換えたりしない。

## 参照解決

`business-records.json`の`key`は論理レコード識別子。`values`には次の参照表現が含まれる。

| 表現 | 解決先 |
|---|---|
| `$record` | このbundleの論理キーに対応する、対象環境の作成済み／再利用済みID |
| `$external` | 外部参照表の業務キーで照合し、ユーザーと確定した既存ID |
| `$record_type` | 対象オブジェクトとDeveloperNameで一致する有効・利用可能なRT ID |
| `$actor` | 認証済みの対象環境のシステム管理者のUser ID |
| `$profile` | 対象環境にある同名の既存プロファイルID（Userモード） |
| `$username` | target_org_idとStaffIDを使って生成した組織間で一意のUsername |

対象スキーマの参照先型も検証する。論理記号、ソースID、ソースProfileId／RecordTypeIdをそのまま送信しない。外部参照の上書き対応をユーザーが指定した場合も、対象の有効性、プロファイル区分、所属を確認する。

## 重複識別と再実行

- AccountはCIF、関係機関はCIF、各業務オブジェクトは既存ExternalId等で検索。対象側に外部IDとして定義されていなくても、単なる一意のデータ検索キーとして使うことはできる。フィールド設定を変更しない。
- `approved_composite_or_journal_required`の事例、アプローチ、会社概要、総称マスタ、紹介者、相談等は、投入前にオブジェクトごとの識別条件を決める。例：親顧客＋事業上の種類、事例タイトル＋分類＋支店＋本文照合。自動採番Name、Name単独、日付だけを一意キーにしない。
- ローカルジャーナルの論理キー→対象IDは、同じ組織ID・bundleハッシュの実行だけで再利用する。存在確認と業務キーの照合を行う。複数の元レコードを1つの対象レコードへ集約する判断は勝手に行わない。
- 重複が一意に確定した既存レコードは更新せずスキップし、対応IDを記録する。内容が違う等の判断材料があれば確認する。
- `DUPLICATES_DETECTED`はルールを回避しない。照合・親の対応が未確定になったら全書込みを停止し、判明した成功分を記録して質問する。
- タイムアウト・切断時は再送前に業務キーとジャーナルで作成済みか確認。確定できなければ停止。

## 段階投入

論理参照から依存グラフを作り、親が解決できるものだけを順次投入する。

1. 既存支店・部署・窓口・担当者・RT・プロファイル照合。必要な場合のみ別モードでUserを作成。
2. 顧客、関係機関と参照元、総称マスタ・協調融資商品など独立した業務データ。
3. 顧客・関係機関の明細、活動管理、貸付金元帳。
4. 元帳明細、借入申込、顧客タスク、相談、事例、交渉履歴等。
5. 上位機関・紹介者等の相互参照。新規作成したレコードだけへ、必要な参照の後付けを行う。
6. 相談資料は顧客IDが解決してからContentVersionを作成し、文書と顧客リンクを読戻し確認。

循環参照の後付けは項目がnullableかを確認。必須の循環なら停止する。通常の投入では既存重複のレコードへPATCHしない。既存データ補完を明示された場合だけ、`authorized_update_ids`と`authorized_update_fields`の両方へ対象IDと承認項目を記録する。既存文書の新バージョンも別途明示された場合だけ`authorized_document_update_ids`へ登録する。

## 検証と出力

対象環境の作成可能項目だけへ投入する。システム監査項目や計算項目は送信しない。元データで値がある項目を、先環境にないという理由で黙って落とさない。

必要な確認：1862件の計画・作成・スキップ・未実施の照合、同一顧客／関係機関のCIFと参照元、対象顧客ごとのオープン融資／債権管理各1件、名称固定、Taskの直接顧客参照0、債権連携の意味・接触区分、金額・日付・法人番号等の整合、添付資料6件と顧客リンク。既存データがこの構成と矛盾する場合に勝手に閉じたり書き換えたりしない。

出力はオブジェクト別CSV、論理キー対応表、実行結果、スキップ・保留理由、保存値確認。CSVにOwnerIdは入れない。見やすい一覧が必要なら利用可能なSpreadsheetsスキルを適用する。設定・権限の変更や実画面確認を行っていない場合に、行ったと報告しない。
