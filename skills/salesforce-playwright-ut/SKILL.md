# Salesforce単体テスト実行

Excel出力時は [references/evidence-format.md](references/evidence-format.md) の表示補正を適用する。数式ケースはケース情報直下のA6から画像を連続配置し、3時点の見出し・空き領域を設けない。全ケースNoタブを色なしにし、「（ここにエビデンス添付）」を全シートから削除する。入力規則の3時点見出し・画像配置は保持する。

Excel仕様書・設計書を期待値の正本とし、既存コードを使って画面結果、設定照合、正しい位置の赤枠画像を対応付ける。過去の成功は今回の接続先・ユーザー・保存状態の証明にしない。

入力規則テストでは、未指定の検証対象外の必須項目を基準レコードに従って入力する。一方、仕様書で指定された空欄・基準値は保持し、画面必須チェックや別の入力規則が先に働いて期待結果と異なる場合もNGとして記録する。実際のエラーと対象規則への到達状況を併記し、条件を変更して成功扱いにしない。

現時点の実装と確認済み手順を再利用するスキル。現行資料でスキルを作成・利用し、完成版の提出を待たない。情報不足は都度質問せず、[references/assumptions.md](references/assumptions.md) に従い根拠付きの想定と実行方法を決める。実施した想定テストは「前提付きOK／前提付きNG」として条件・実施内容・限界を残す。未実装の処理は承認範囲で追加して実行し、未実行を成功扱いにしない。完成版・改訂版の資料では [references/specification-changes.md](references/specification-changes.md) に従って再読込・手順の対応確認・必要な追加実装を行う。顧客の現行60ケースの画面／代替検証と一括実行は [references/customer-current.md](references/customer-current.md) を読む。数式・入力規則の抽出・ZIP照合・結果出力は [references/all-rule-formula.md](references/all-rule-formula.md) を読む。

ボタン表示条件を実施するときは [references/button-visibility.md](references/button-visibility.md) を読み、オブジェクト設計書・画面イメージ・権限設計書から対象ボタンとプロファイル別期待値を対応付ける。1ケースに複数プロファイルが含まれる場合も、全対象プロファイルの代理ログイン・画面判定・キャプチャを個別に取得し、同じケースNoシートにまとめる。

## 実行担当のモデル・推論深度

- Salesforceテストの実行担当は **GPT-6 Astra・推論深度high** のエージェントとする。業務データ準備、接続確認、画面・API操作、実測・撮影、再開・復旧まで、この担当に委任する。親エージェントは資料解析、実行調整、結果集約・出力確認を行う。
- `collaboration.spawn_agent` では `model: "gpt-6-astra"`、`reasoning_effort: "high"` を明示する。モデル・推論深度を指定できる `fork_turns: "none"` または正のターン数を使い、担当へ本SKILL.mdの絶対パス、ワークスペース、対象ケース、最新版資料・メタデータ、再開元runとpendingの有無を渡す。
- 実機ブラウザーを操作する担当は同時に1エージェントとし、ケースは順次実行する。複数エージェントを使う場合は資料解析・メタデータ照合・出力確認を並列化し、実機操作の引継ぎ時は前担当の停止と保存状態を確認する。
- 指定モデル・推論深度で担当を起動できない場合は、実機テストを開始せず理由を報告する。モデル指定は担当エージェントの起動設定で行い、親チャットの設定変更と混同しない。

## 操作範囲

- Salesforce設定とUserレコードは全工程で参照専用。姓・権限・入力規則・Flow等を変えて条件を作らない。設定変更が必要なケースは理由付き保留。
- 業務テストデータは専用レコードを自動作成する。参照先も必要に応じて先に作成する。準備は認証済みSandboxの業務データAPI、仕様書が検証する入力・保存はPlaywright画面操作で行う。[references/test-data.md](references/test-data.md) を読む。User・設定オブジェクトは作成・更新対象にせず、終了後に自動削除しない。別案件へこの案件の変更許可を持ち込まない。
- 通常実行の閲覧履歴等は案件の承認範囲で許可し、設定・User更新と区別する。未知の更新を包括許可しない。
- 管理者は手動ログインし、管理者以外は実画面の代理ログイン機能を使う。資格情報をチャット・Excel・ログに書かない。永続プロファイルは案件の承認がある場合だけ使う。MCPは初回調査・他の手段で特定不能な調査に限定し、自動切替しない。
- 原本は保持。結果は仕様書のコピー。エビデンスと結果記入済み仕様書のコピーは evidence-format.md の命名規則に従い、仕様書名＋出力日時の同じフォルダに格納する。エビデンスは仕様書ごとに1冊、B列「ケースNo」ごとに1シート。[references/evidence-format.md](references/evidence-format.md) に従い、入力規則・数式・ボタン表示条件とも `エビデンス出力用のテンプレ.xlsx` を複製してケース情報と画像を配置する。入力規則は実施前・実施・実施後を各1枚基本で必要最小限、数式の撮影対象は従来のページレイアウト／開発者コンソールを維持する。ボタン表示条件は対象プロファイルごとのボタンまたは配置領域の実画面を取得し、同じケース・枝番内にプロファイル名・対象ボタン・期待表示・実表示を添えて配置する。最新判定は実施一覧に記載する。他の説明は実施一覧の備考にまとめる。詳細履歴・設定照合はローカル結果に保持する。枝番ごとにシートを分けない。動画・trace・独自ログの外部送信を追加しない。

## 実行手順

1. **対象を確定する。** 国民CRMでは [references/project.md](references/project.md) を読む。別案件ではその固定値・許可・成功実績を持ち込まず、その案件の接続先、資料、アカウント、更新許可を確認する。`テスト参照資料一覧.xlsx`から仕様書・オブジェクト設計書・画面イメージ・権限設計書・メタデータの参照先を読む。[references/test-scope.md](references/test-scope.md) と `scripts/select_test_scope.py` で数式項目・入力規則・ボタン表示条件の対象IDを確定する。権限設計書は `scripts/permission_reference.py` で現行一覧から解決し、資料ハッシュと参照箇所を保存する。メタデータの読込方針は project.md に従う。画面打鍵の前にローカル確認を行う。
   ```powershell
   & $pythonExe (Join-Path $skillDirectory 'scripts/check_workspace.py') --workspace $workspacePath --run $parentRunId
   ```
   `$skillDirectory`は読み込んだ本スキルの絶対ディレクトリ、他の変数は利用可能なPython・対象フォルダー・再実施元ID。新規実行は`--run`を省略する。成功はローカル前提確認だけで、ログイン・実機組織照合ではない。未確認の保存は参照による状態確認へ進む。
2. **接続を確認する。** VPNを維持し、専用EdgeのループバックCDP・プロファイル所有者を確認する。起動済みEdgeを再利用し、終了時は自分の通信制御のみ解除する。起動・ログインが必要な場合だけ execution.md の2段階で利用者へ案内し、バッチと同じ完了基準・返信文言を使う。画面で組織ID・Sandbox・実ユーザー名・姓を照合してから変更操作を始める。
3. **単一ケースを実行する。** [references/execution.md](references/execution.md) の対象指定コマンドを使う。順次実行し、対象要素・保存結果を待つ。設定ケースは成功・不一致の両方でメタデータを照合し、設計書から期待値を決める。現在の設定を期待値に置換しない。
4. **正常終了を検証する。** 画面・メタデータ判定を別々に残す。明示的期待値との不一致はNG。想定で補ったテストは実測結果に基づき前提付きOK／NG。未完了・自動化エラーは実行状態として分離し、製品のNGや想定テストの成功に置換しない。確認済みNGを他の未完了で隠さない。通信エラー表示を伴う画像でOKにしない。No.58枝番4は保存後の追加参照確認まで行う。
5. **Excelを検証する。** ボタン表示条件では計画した全ボタン×全プロファイル×条件に結果と実画面画像があるか `scripts/validate_button_evidence.py` で照合し、未取得を保留として残す。 [references/evidence-format.md](references/evidence-format.md) の最新入力・出力形式を使い、枝番・判定・画像の対応を確認する。入力値と出力結果の赤枠をそれぞれ目視し、保存済みExcelの埋め込みも確認する。ケース情報が保存した仕様書の該当ケース・枝番と一致し、テンプレートの書式・画像添付領域・撮影時点を満たすことを確認する。詳細な実結果・日時・設定照合・想定・履歴はローカル結果で対応を保持する。原本ハッシュ、コピーの書式・数式、実施者・承認者の空欄を保持する。再出力のためにテストを再実行しない。

## 異常時の分岐

- **数式項目・入力項目がレイアウトにない**：[references/query-evidence.md](references/query-evidence.md) の開発者コンソールSOQL照合と結果画面撮影を優先する。実レコードの入力・計算結果・実行ユーザー条件を確認できたケースをOK／NGへ更新する。

- **通信エラー／ブラウザー終了／タイムアウト**：他ケースへ進まず [references/recovery.md](references/recovery.md) の参照診断を使う。エラーを閉じるだけで解消扱いにしない。IP制限を推測で原因断定せず、SalesforceやPCの設定を勝手に変更しない。
- **保存途中で切断／スリープ**：`pending`、対象ID、予定値を確認し、読み取りだけで保存状態を照合する。保存を無条件に再送しない。回復した失敗試行は保留を維持し、再実施は新しい試行として残す。
- **赤枠ずれ**：[references/recovery.md](references/recovery.md) の画像修正を使う。過去画像を現在のDOM座標で修正しない。元画素で確認した位置だけを直し、元画像・旧注釈・判定履歴を保持する。
- **設定取得不能／条件ユーザーなし**：独立した代替検証が可能なら想定と未検証範囲を明記して実施する。必須の設定照合が未取得なら未完了を残し、一致扱いにせず、設定変更やMCPへの自動切替で通さない。

- **代理ユーザーのAPI権限不足**：既存のプロファイル・権限セットのAPI権限を読み取り確認してからユーザー属性数式を計画する。API利用可能なCookieが管理者のものであっても、代理ユーザーの実計算の証明には使わない。新規クエリの認証主体が対象ユーザーであることを照合する。API有効化やUser属性更新はせず、画面による独立検証がない場合は未完了として理由を残す。

## 完了の基準

ボタン表示条件は必要な全プロファイルの本人照合・表示有無判定・実画面キャプチャ・Excel埋め込みがそろった範囲だけを実施済みとする。1プロファイルの成功をケース全体へ広げない。

今回の対象全体で期待値、必要な設定照合、保存状態、通信エラーのない結果画像、正しく囲む赤枠、Excel埋め込みを確認して初めてOKを報告する。ローカル検証・過去の成功・一部対象の成功を実機全体の成功に広げない。再発ゼロは保証せず、未確定原因・未実施範囲を明記する。

想定による判定は実施した範囲に限る。ローカル数式検証をSalesforce画面での成功と表示しない。認証・操作許可が足りない場合の確認は、仕様の不足に対する都度確認とは区別する。
