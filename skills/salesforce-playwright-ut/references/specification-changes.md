# 完成版・改訂版仕様書での実行

実行・追加実装・準備・出力の対象は [test-scope.md](test-scope.md) で確定したIDに限る。以下の「全件」「未対応」「継続」はこの対象内を意味する。

## 現行資料から新しい実行を作る

1. 一覧Excelのパスが完成版の仕様書・設計書を指していることを確認し、`automation/実行.ps1 catalog` で実ファイルを再読込する。従来の52ファイル・2,602行・1,169対象行は過去の件数であり、完成版の件数を固定しない。
2. B列ケースNo・C列枝番、カテゴリ、G列の明示的確認対象、前提、入力、操作、期待結果、未確定事項を読む。ボタン表示条件は [button-visibility.md](button-visibility.md) に従い、権限設計書も再読込してケース内の全対象プロファイルを展開する。数式・入力規則は設計書のAPI名・定義・エラー文言・表示場所と対応付ける。行位置や旧ケースNoだけで以前のコードへ結び付けない。
3. `catalog` の欠落・重複、参照元ハッシュ、一覧ハッシュを確認する。資料変更がある場合は新規 `run` を使用し、旧IDの `resume`・`rerun` に新しい資料を混ぜない。以前の結果・画像・コピーは以前の資料版の履歴として保持する。
4. 設定も更新途中の場合、使用するZIPの取得元・日時を確認する。同じZIPの再読込と現行組織からの再取得を区別する。組織は照合し、Salesforce設定を変更して資料へ合わせない。

## 手順の適合・追加実装

現在の画面基盤は顧客の一部ケースに対応し、全オブジェクトの入力規則・数式・ボタン表示条件用画面ハンドラーが完成しているわけではない。スキル利用時には現在のコードと完成版の条件を照合し、未対応のものは承認済み範囲で手順を追加する。資料不足の扱いは assumptions.md を適用し、完成版を待たず現行資料で実行計画を作る。

- 新規・変更ケースは「対象オブジェクト／項目・規則API名／枝番の条件／入力値／期待値／使用ユーザー／必要な親・マスタ／画面操作／証跡位置」の実行計画を作る。
- 分岐・境界値・日付条件は完成版の期待値から決める。現行メタデータから正解を作らない。TODAY等は現在の日付と仕様書の基準日を照合する。固定日付を実機で再現できない場合は、日付変更をせず、現在日付に対応する入力での画面検証と固定日付のローカルロジック検証を分け、代替手順と限界を記録する。
- 実装済みでも入力・操作・期待値が変更されていれば、その変更に合うローカル検証を行ってから実機の単一ケースを試す。未実装や要素未確認を実施済みと記録しない。
- Userレコードや設定の変更を必要とする前提は理由付き保留。既存ユーザーの条件を参照で確認し、管理者以外は既存の代理ログインを使う。
- `safety.ts` の対象・項目・操作範囲は既存承認と照合してから追加する。未知の更新を包括許可する方法で画面を通さない。新たな業務データの更新範囲が不明な場合は、その対象だけ確認を求める。
- 設定画面の参照が仕様書の手順なら参照を実装し、メタデータへの置換を行う場合は今回の想定実施の承認に基づく手順変更として理由・元手順・代替方法・未検証の画面操作を記録する。無記録で省略しない。保存は対象の入力規則・数式ロジックの検証手順に従う。親削除等の独立ケースはこのスキルの対象外。

## 実行と出力

設定照合全体は `report-all-rule-formula.ts` を引数なしで実行して新規IDに保存する。画面実行は、今回の資料で確認したケースIDを `automation/実行.ps1 run --cases <ID一覧> --profile <回答Excelのプロファイル>` に指定する。未対応ハンドラーは保留として記録されるので、対象を指定しただけで実装済みになるとは扱わない。

未確認保存がある場合は参照照合を先に行う。通信エラーを含む画面は正常証跡にしない。ボタン表示は単一 `--profile` の実行だけで全プロファイル確認済みと扱わず、計画した全対象プロファイルの試行を保存・集約する。既存の数式・入力規則専用照合処理をボタンの実画面証跡として流用しない。まず一連の単一ケースを通して、枝番や対象・プロファイルを順次広げる。

エビデンスは各仕様書に1冊。`ケースNo58` のようなシートはB列ケースNo 58に対応し、枝番1・2・3・4はシート内の独立した区画に記録する。ケースNoが変更されたら新しい番号のシートを作る。他の仕様書の同じ番号とは混ぜない。画面画像・設定照合・NG・保留・再実施履歴も対応する枝番区画へ入れる。出力manifestの枝番ごとの開始・終了行で対応を検証する。

保存済み結果の再出力は、保存時のcatalog・state・画像・メタデータを使い、Salesforceを再操作しない。コピー再生成時に元仕様書が変更済みなら、元のハッシュと一致する保存版が必要。変更後の原本を旧結果で上書きしない。


## 参照設計書の再保存だけでハッシュが変わった場合

旧実行のハッシュを上書きしてresumeしない。`continue-unchanged-customer.ts <旧クエリ実行ID>`は、仕様書原本・全顧客ケース・読み込んだ設計定義・参照先パス・メタデータZIPが同一でpendingがない場合だけ、新しい資料ハッシュを持つ継続実行を作る。変更前後のハッシュと元実行の履歴を保存する。ケース／読込定義の差異が一つでもあれば拒否し、新規計画・実行へ進む。旧画像は過去の実測として対応を保持し、今回再撮影したと記載しない。

`combine-customer-results.ts <数式実行ID> <入力規則等の実行ID> ...`は同一の顧客原本・ケース・設計定義でpendingのない保存済み結果だけをローカル統合する。元実行・元試行番号と画像保存先を維持し、後続結果を新しい試行番号へ対応付ける。統合・Excel再出力はSalesforce操作を行わない。

`テスト参照資料一覧.xlsx`を再読込し、メタデータの参照先も project.md に従って解決する。一覧Excelはアクティブシートや先頭シートを仕様書一覧と決めつけない。`catalog.py`は「テスト仕様書のファイル名」「テスト仕様書の格納先のパス」を持つシートを一意に選び、メタデータ一覧は仕様書として解析しない。2026/10/05にメタデータを先頭にした現行一覧で52仕様書・2,602ケース行を再読込し、顧客原本・全顧客ケース・設計定義が従来と同一であることを確認した。選択ケースの定義・対象規則が存在しない場合は、ブラウザー操作・専用データ作成を開始しない。

顧客専用ランナーは`catalog("O01")`で顧客原本と顧客参照資料だけを再読込する。全件読込は引数なしのcatalogを維持する。対象外の設計書の一時ロックが顧客実行を妨げないようにし、対象の原本・設計書のハッシュ照合を省略しない。対象資料自体が読めない場合は実行しない。全52仕様書を実行したとの表示に置換しない。
